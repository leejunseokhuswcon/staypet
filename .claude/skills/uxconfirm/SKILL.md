# uxconfirm — UI 이전에 UX를 확정하는 절차

UI 품질은 UX 구조의 함수다. 구조가 틀린 상태에서 만든 화면은 "보기 좋은 실패작"이 되고, 수정 비용은 코드가 쌓일수록 커진다. 이 스킬은 **화면을 그리기 전에 사용자 머릿속에서 일어나는 일을 먼저 확정**하기 위한 절차다.

## 운영 원칙

1. **UI 산출물을 만들지 않는다.** 이 스킬이 도는 동안 컴포넌트 코드, 스타일, 레이아웃 시안, 색/폰트/간격 제안을 내지 않는다. 산출물은 UX 분석 문서 하나다.
2. **화면 단위로 끝내지 않는다.** 화면 분석은 골격일 뿐이고, 실제 실패는 개별 element에서 난다. 화면당 핵심 Interactive Element를 모두 뽑아 **각각 독립적으로** 흐름을 검증한다.
3. **추측을 사실처럼 쓰지 않는다.** 도메인·사용자·비즈니스 조건이 불확실하면 먼저 묻는다. 물을 수 없으면 해당 문장 앞에 `[가정]`을 붙여 검증 대상임을 남긴다.
4. **사용자 문장으로 쓴다.** "필터 컴포넌트를 제공한다"가 아니라 "사용자는 '우리 집 근처에 지금 맡길 수 있는 곳'을 찾고 싶다"로 쓴다. 기능 명세는 UX 분석이 아니다.
5. **승인 게이트로 끝난다.** 분석 후 사용자의 확인을 받기 전까지 다음 단계(와이어프레임·UI·구현)로 넘어가지 않는다.

## STEP 0 — 컨텍스트 확보

분석 전에 이것부터 확인한다. 프로젝트에 문서가 있으면 추측보다 문서를 먼저 읽는다(`README`, `CLAUDE.md`, `docs/`, 기존 라우트·화면 파일, 상태/스토어 정의).

- 대상 범위: 어떤 화면 또는 어떤 플로우인가
- 사용자 세그먼트: 누가 쓰는가 (예: 신규/재방문, 맡기는 쪽/맡아주는 쪽, 앱 첫 실행/재실행)
- 진입 경로: 사용자는 어디서 이 화면으로 오는가 (푸시, 딥링크, 이전 화면, 검색, 콜드스타트)
- 성공 정의: 이 화면이 성공했다는 걸 무엇으로 판단하는가
- 제약: 로그인 필요 여부, 결제·예약·실시간성 등 되돌릴 수 없는 동작 포함 여부

모르는 항목이 3개를 넘으면 분석을 시작하기 전에 **질문 3개 이내로 묶어서** 먼저 묻는다.

## STEP 1~5 — 화면 골격 분석

순서를 지킨다. 뒤 단계가 앞 단계의 답과 모순되면 앞으로 돌아간다.

1. **사용자 목표** — 사용자가 이 화면에서 끝내고 싶은 일 한 문장. 앱의 목표가 아니라 사용자의 목표다. 목표가 2개 이상이면 화면이 2개일 가능성을 의심한다.
2. **화면 진입 이유** — 어떤 상태·감정·미해결 질문을 안고 들어오는가. 진입 경로별로 기대가 다르면 경로별로 나눠 쓴다.
3. **가장 먼저 인지해야 하는 정보** — 3초 안에 사용자가 확인해야 하는 정보 1~3개. 이게 화면에서 시각적 1순위가 아니면 구조 문제다. "내가 맞는 곳에 왔다"는 확인이 여기 포함되는지 본다.
4. **핵심 CTA** — 이 화면이 유도하는 단 하나의 행동. 후보가 여럿이면 우선순위를 정하고, 2순위 이하는 왜 남겨두는지 근거를 쓴다. 사용자가 CTA를 누르기 전에 반드시 해소돼야 하는 불안/의문이 있으면 함께 적는다.
5. **Interactive Element 식별** — 화면 내 상호작용 가능한 요소를 전부 나열한다. 버튼·링크·입력·선택·토글·필터·정렬·카드/리스트 아이템·탭·모달·바텀시트·스와이프/드래그·지도 핀·업로드·알림 배너 등. 각 element에 `핵심 / 보조 / 제거 후보` 등급을 매기고, **핵심으로 분류한 것은 STEP 6을 전부 수행한다.**

## STEP 6 — Element별 UX Flow (핵심 단계)

핵심 Element마다 아래 12항목을 **하나도 빠뜨리지 않고** 채운다. 항목이 "해당 없음"이면 그렇게 쓰되, 왜 없는지 한 줄 근거를 남긴다. 빈칸은 대체로 미설계 지점이고, 실제 버그와 이탈은 거기서 나온다.

| # | 항목 | 검증 질문 |
|---|---|---|
| 1 | 인지 | 이 요소가 있다는 걸 어떻게 알아채는가? 스크롤·탭 전환 없이 보이는가? 라벨만 보고 결과를 예측할 수 있는가? |
| 2 | 사용 동기 | 왜 이걸 누르는가? 사용자의 어떤 질문·불안·욕구에 대응하는가? |
| 3 | 사용 전 기대 | 누르기 직전 사용자가 예상하는 결과는? (화면 이동인가, 값 변경인가, 되돌릴 수 있는가) |
| 4 | 조작 방식 | 탭/롱프레스/스와이프/드래그/입력/스크롤 중 무엇인가? 손가락 도달 범위와 오조작 가능성은? |
| 5 | 즉각적 피드백 | 누른 직후 100~300ms 안에 무엇이 바뀌는가? 처리 지연 시 무엇을 보여주는가(스켈레톤/스피너/낙관적 업데이트)? |
| 6 | 성공 상태 | 성공했다는 걸 무엇으로 아는가? 결과가 화면 밖에서 일어나면 어떻게 알리는가? |
| 7 | 실패/오류 상태 | 실패 유형(네트워크, 검증, 권한, 서버, 충돌)별로 무엇이 보이는가? 메시지가 원인과 다음 행동을 함께 말하는가? |
| 8 | 취소/되돌리기 | 실행 전 취소, 실행 후 되돌리기가 가능한가? 불가능하면 사전 확인이 필요한 수준의 행동인가? |
| 9 | 재조작 | 다시 누르면 어떻게 되는가? 연타·중복 제출·중복 결제는 어떻게 막는가? |
| 10 | 다음 상태 | 조작 후 사용자는 어디에 있는가? 화면·스크롤 위치·입력값·선택값은 유지되는가? |
| 11 | 필요성 | 이 element가 없으면 사용자는 목표를 못 이루는가? 못 이룬다면 남기고, 이룬다면 제거 후보다. |
| 12 | 대체 가능성 | 더 직접적인 상호작용으로 바꿀 수 있는가? (모달 → 인라인 편집, 별도 화면 → 바텀시트, 선택 후 확인 → 즉시 반영 + 되돌리기, 입력 → 기본값 제안) |

**작성 예시 (형식 참고용, 내용은 실제 화면에 맞게 다시 쓸 것)**

> **Element: [예약하기] 버튼 (핵심)**
> - 인지: 하단 고정 바에 상시 노출. 단 가격이 스크롤 영역 안에만 있어 버튼과 가격을 동시에 볼 수 없음 → 인지-결정 분리 문제.
> - 사용 동기: 조건이 맞는 곳을 찾았고 확정하고 싶다.
> - 사용 전 기대: 바로 확정이 아니라 "확인 단계가 한 번 더 있겠지"를 기대함. 실제로 즉시 확정이면 기대 불일치.
> - 즉각적 피드백: 현재 없음 → 서버 응답까지 무반응 구간 발생, 연타 유발.
> - 재조작: 중복 요청 차단 미정의 → P0.
> - 대체 가능성: 확인 모달 대신 버튼 내 2단계 확정(슬라이드 또는 확정 후 5초 되돌리기)으로 단계 1개 제거 가능.

## STEP 7 — 구조 레벨 검증

Element 분석이 끝나면 화면/플로우 전체를 아래 9개 축으로 다시 본다.

- **인지 부하** — 한 화면에서 요구하는 판단의 개수. 동시에 비교해야 하는 정보가 3개를 넘는가? 기본값으로 대신할 수 있는 선택은 없는가?
- **불필요한 단계** — 사용자가 이미 말한 정보를 다시 묻는 곳, 시스템이 추론 가능한 입력, 나중에 물어도 되는 질문.
- **화면 병합 가능성** — 인접한 두 화면이 같은 판단을 위한 정보라면 합칠 수 있는가? 반대로 서로 다른 목표가 한 화면에 섞여 있으면 분리한다.
- **뒤로가기/수정** — 뒤로 갔을 때 입력·선택·스크롤이 보존되는가? 중간 단계로 직접 돌아가 수정할 수 있는가, 아니면 처음부터 다시인가?
- **오류 복구** — 실패 후 사용자가 몇 번의 조작으로 원래 지점에 복귀하는가? 입력값이 날아가는 지점은 없는가?
- **Empty / Loading / Error** — 세 상태를 모두 정의했는가? Empty는 "왜 비었는지 + 다음 행동"을 주는가? Loading은 예상 시간과 취소 가능성을 알려주는가?
- **이탈 가능 지점** — 사용자가 그만둘 만한 지점과 그 이유(불안, 대기, 재입력, 요구되는 노력, 로그인/결제 벽). 각 지점에 완화 장치가 있는가?
- **기대와 실제 동작의 불일치** — 라벨·아이콘·위치가 암시하는 결과와 실제 결과가 다른 곳. 되돌릴 수 없는 동작이 되돌릴 수 있게 보이는 경우는 즉시 P0.
- **첫 핵심 가치까지 걸리는 시간(TTFV)** — 진입부터 사용자가 "이거 쓸만하다"를 느끼는 순간까지 필요한 화면 수·탭 수·입력 수. 이 값을 줄이는 방법을 최소 1개 제안한다.

## STEP 8 — 문제 정리와 개선안

발견한 문제를 우선순위로 묶는다. 각 항목은 **문제 → 사용자에게 생기는 결과 → 개선안 → 확인 방법** 순서로 쓴다.

- **P0** — 사용자가 목표 달성에 실패하거나, 되돌릴 수 없는 손해(중복 결제, 잘못된 예약, 데이터 유실)가 생김
- **P1** — 달성은 하지만 이탈률·오조작·재작업이 크게 늘어남
- **P2** — 개선하면 좋지만 목표 달성에는 지장 없음

개선안은 UI 시안이 아니라 **구조 변경**으로 쓴다. ("버튼을 크게" 가 아니라 "확정 전 확인 단계를 제거하고 실행 후 되돌리기 5초를 제공한다")

## STEP 9 — 승인 게이트

분석 마지막에 항상 아래를 실행한다.

1. 확정이 필요한 결정 사항을 **선택지 형태**로 3개 이내 제시한다.
2. `[가정]`으로 표시한 항목을 모아 확인을 요청한다.
3. 다음 문장으로 마무리한다: **"이 UX 구조를 확정하면 다음 단계(와이어프레임/UI)로 넘어가겠습니다. 수정할 부분을 알려주세요."**
4. 사용자의 확정 응답 전에는 UI·컴포넌트 작업을 시작하지 않는다.

## 출력 형식

항상 이 구조로 출력한다. 요청 범위가 여러 화면이면 화면별로 반복한다.

```markdown
# UX 검증: [화면/플로우 이름]

## 0. 전제
- 사용자 세그먼트 / 진입 경로 / 성공 정의 / [가정] 목록

## 1. 사용자 목표
## 2. 화면 진입 이유
## 3. 가장 먼저 인지해야 하는 정보
## 4. 핵심 CTA
## 5. Interactive Element 목록 (핵심/보조/제거 후보)

## 6. Element별 UX Flow
### 6-1. [Element 이름] (등급)
- 인지 / 사용 동기 / 사용 전 기대 / 조작 방식 / 즉각적 피드백 /
  성공 / 실패·오류 / 취소·되돌리기 / 재조작 / 다음 상태 /
  필요성 / 대체 가능성
### 6-2. ...

## 7. 구조 레벨 검증
- 인지 부하 / 불필요한 단계 / 화면 병합 / 뒤로가기·수정 / 오류 복구 /
  Empty·Loading·Error / 이탈 지점 / 기대 불일치 / TTFV

## 8. 문제 및 개선안
| 우선순위 | 문제 | 사용자에게 생기는 결과 | 개선안 | 확인 방법 |

## 9. 확정 필요 사항
- 결정 1 / 결정 2 / 결정 3
```

분석 결과를 파일로 남길지 사용자에게 확인한 뒤, 원하면 `docs/ux/<flow-name>.ux.md`로 저장한다.

## 자주 나오는 실패 패턴

작성 중 아래에 해당하면 그 부분을 다시 쓴다.

- Element 목록이 화면에 있는 컴포넌트 목록과 같다 → 사용자 관점이 아니라 구현 관점으로 쓴 것이다.
- 12항목 중 실패·취소·재조작이 반복적으로 비어 있다 → 해피 패스만 설계한 것이다.
- 개선안이 전부 "잘 보이게", "명확하게" 같은 형용사다 → 구조 변경이 아니라 감상이다.
- 모든 element가 "필요함"으로 판정됐다 → 필요성 질문을 실제로 하지 않은 것이다. 최소 1개는 제거·병합 후보를 검토한다.
- 화면 수가 늘어나는 방향으로만 개선안이 나온다 → 병합과 인라인 전환을 검토하지 않은 것이다.

## 이 스킬이 하지 않는 것

색상, 폰트, 타이포 스케일, radius, shadow, gradient, 간격 토큰, 아이콘 스타일, 애니메이션 커브, 컴포넌트 코드. 시각 디자인은 UX 구조가 확정된 뒤 별도 단계에서 다룬다. 사용자가 이 스킬 실행 중에 UI를 요청하면, 남은 미확정 항목을 먼저 알리고 확정 여부를 확인한 뒤 넘어간다.
