## 0. 총평 — Codex안의 체계적 편향 하나

개별 항목을 보기 전에, Codex안 전체를 관통하는 **방법론적 누락**을 먼저 지적한다. 이것이 이후 15개 항목에서 반복되는 문제 대부분의 공통 원인이기 때문이다.

### 0.1 검증된 사실

Codex안 4장은 53개의 Element Flow를 담고 있고, **53개 전부가 다음 11개 항목으로 끝난다.**

`인지 → 사용 동기 → 기대 → 조작 → 즉각적 피드백 → 성공 → 실패/오류 → 취소/되돌리기 → 재조작 → 다음 상태 → 존재 필요성`

즉 **12번째 축인 "대체 가능성"(이 element를 더 단순하고 직접적인 상호작용으로 바꿀 수 있는가)이 53개 element 전부에서 빠져 있다.** 문서 전체에서 `대체 가능성`이라는 검증 축은 단 한 번도 등장하지 않는다.

### 0.2 그 결과로 나타난 편향

11번 `존재 필요성` 슬롯의 판정을 모두 훑어보면, "필요 없다 / 제거한다"는 결론이 나온 17개 항목이 **거의 전부 "별도 화면일 필요는 없다", "독립 화면은 불필요하다", "별도 버튼은 불필요하다"** 형태다. 정리하면:

| Codex안이 실제로 제거한 것 | 개수 |
|---|---|
| 화면·단계(같은 조작을 다른 화면에 옮기거나 병합) | 대부분 |
| 상호작용 자체(조작 난이도를 낮추는 치환) | **동영상 `건너뛰기` 1개** (그것도 화면 병합의 부산물) |
| 새로 추가한 element | **실행 취소/다시 실행 1개** (추가) |

**즉 Codex안은 "화면 수는 줄였지만 사용자가 배워야 할 조작의 총량은 거의 그대로 두었고, 일부는 오히려 늘렸다."** 11번 항목만 물으면 "이 element가 없으면 목표를 못 이루는가?"라는 질문에 대부분 "못 이룬다"가 나온다. 그래서 답이 자연스럽게 "유지 + 화면만 병합 + 복구 도구 추가"로 수렴한다. 12번 항목을 물었다면 "이 조작을 더 쉬운 조작으로 바꿀 수 있는가?"가 검토됐을 것이고, 최소한 §5(이동 영역), §9(쓰다듬기), §14(보정)에서 다른 결론이 나왔어야 한다.

### 0.3 두 번째 관찰 — 결정 유예의 위치

`미확정` / `사용자 결정이 필요` / `기술 검증 필요` 표기가 문서 전체 40여 곳에 등장한다. 유예 자체는 AGENTS.md 원칙("제품 정책이 모호하면 추측해서 확정하지 마라")에 맞고 옳다. 문제는 **유예된 항목이 하필 그 element의 성패를 좌우하는 슬롯에 몰려 있다**는 점이다.

- 이동 영역 Brush(4.6.2) — 4번 `조작` 슬롯: "사진 확대·이동은 Brush와 충돌하지 않는 별도 제스처 규칙이 필요하다" → **조작 방식 자체가 미정**
- 후보 카드(4.5.2) — 4번 `조작` 슬롯: "세부 확인용 확대 제공 여부는 사용자 결정이 필요하다" → **유사도 판단의 핵심 수단이 미정**
- 첫 만남(4.7.4) — 4번 `조작` 슬롯: "건너뛰기·가속은 사용자 결정이 필요하다" → **최대 감정 정점의 통제권이 미정**

한 element에서 1·2·3번(인지·동기·기대)은 촘촘하고 4번(조작)이 비면, 그 분석은 **"왜 필요한지는 잘 설명했지만 실제로 어떻게 쓰는지는 아직 모른다"**는 상태다. Low-fi에서 검증해야 할 것이 바로 4번인데, Codex안은 그 지점을 다음 단계로 넘겼다.

## 1. 종 선택 / 이름 / 성별 화면 구조

**Codex 제안:** 세 정보를 하나의 `반려동물 기본 정보` 화면으로 통합.

### 판단: **[동의]** — 단, 성별을 P0 필수로 두는 것에는 **[반대]**

통합 자체는 명백히 옳다. 종 선택은 이진 선택, 성별은 소수 선택, 이름은 짧은 텍스트다. 화면 하나당 판단 1개씩을 요구하면서 화면을 3개로 나누는 것은 인지 부하를 줄이는 게 아니라 전환 비용만 만든다. 나는 여기서 Codex안에 반론할 근거를 찾지 못했다.

다만 두 가지를 덧붙인다.

**(1) 화면 안의 순서는 자유롭지 않다.** 종 선택은 문답 4(`짖는 정도` / `우는 정도`)의 문구, 종별 대표 행동, 생성 파이프라인 분기를 결정하는 **선행 조건**이다. 반면 이름·성별은 어디에도 의존하지 않는다. Codex안 3.3도 "종을 먼저 선택해 이후 문구 분기를 안정시킨다"고 쓰지만, 4.2.1~4.2.3의 Element Flow는 셋을 대등한 필드로 다룬다. 한 화면에 두더라도 **종이 먼저 확정되어야 하고, 종을 나중에 바꾸면 문답 4를 다시 확인해야 한다**(Codex안 5.4도 이를 인정한다). 이 의존 관계가 화면 구조에 드러나야 한다.

**(2) 성별은 P0 필수 입력에서 내려와야 한다.** Codex안 4.2.3의 11번 슬롯이 정확히 지적한다: "현재 P0 입력이지만 실제 경험에 미치는 영향은 문서에 없다." 문제는 그렇게 써놓고도 추천 Flow에서는 성별을 필수 입력으로 그대로 유지했다는 점이다. **효과가 정의되지 않은 입력을 필수로 두는 것은 등록 완료율(Activation 지표)을 이유 없이 깎는다.** 셋 중 하나를 줄일 수 있다면 그건 성별이다.

- 개선 방향: 종·이름만 필수, 성별은 같은 화면에 두되 선택 입력으로 내리거나, 성별이 외형·호칭·행동에 실제로 쓰이는 범위를 먼저 정의한 뒤 필수 여부를 결정한다.
- **[가정]** 성별이 생성 프롬프트나 캐릭터 호칭에 실제로 입력되는지 문서에 없다.

## 2. 사진 → 동영상 → 6개 문답의 길이와 순서

**Codex 제안:** 필수 사진·추가 사진·선택 동영상을 하나의 `자료 준비` 단계로 병합하고, 가능하면 사진 검증 직후 생성을 백그라운드로 시작해 문답과 병렬 처리.

### 판단: **[부분 동의]**

**동의하는 부분 — 자료 단계 병합.** `추가 사진이 있나요?`, `동영상을 올릴까요?`를 각각 독립 화면으로 묻는 구조는 선택 자료를 필수 관문처럼 보이게 한다. 특히 독립된 `건너뛰기` 버튼은 그 자체로 "건너뛰면 결과가 나빠지나?"라는 불안을 만든다. 이 진단과 해법 모두 타당하다.

**반대하는 부분 — 병렬 생성을 "기술 검증 항목"으로만 다룬 것.** Codex안 1.5는 병렬 처리를 순수한 기술 가능성 문제로 규정한다("기술적으로 불가능하다면 기존 순서를 유지"). 이건 UX 검토로서 불완전하다. 병렬 처리는 **기술이 가능하더라도 UX 비용을 새로 만든다.**

**(1) 진행 중 요청의 무효화 문제 — Codex안 내부 모순.** 병렬안에서 생성은 사진 직후 시작되고 문답은 그 뒤에 온다. 그런데 Codex안 5.4는 "종 변경 시 외형·종별 행동에 영향을 주므로 후보 재생성 가능성을 안내해야 한다"고 쓴다. 문답 도중 사용자가 뒤로 가서 종이나 사진을 바꾸면, **이미 진행 중인 생성이 무효가 된다.** 5.4는 직렬 Flow를 전제로 쓰였고, 1.5의 병렬 추천과 조정되지 않았다. 병렬화는 "대기 숨기기"라는 이득과 함께 "상위 입력 수정이 진행 중 작업을 깨뜨리는" 새 실패 모드를 만든다. 이건 기술 문제가 아니라 UX 설계 문제다.

**(2) 정서적 톤 문제.** 이 Flow에서 정서적으로 가장 무거운 단일 행동은 사진 업로드다. 떠난 반려동물의 사진을 앨범에서 다시 찾아 고르는 일이다. 그 직후에 즉시 기계적 처리가 시작되는 것이 사용자에게 어떻게 느껴지는지는 문서 어디에도 검증되어 있지 않다. 위로가 될 수도 있고("바로 만들어 주는구나"), 성급하게 느껴질 수도 있다. Codex는 병렬 처리의 효과를 **오직 대기 시간 단축으로만** 평가했다.

**(3) 병렬화가 실패했을 때의 대기 경험이 설계되어 있지 않다.** Codex안 3.6은 "가짜 진행률이나 확정되지 않은 남은 시간을 사용하지 않는다"고 옳게 금지하지만, 대신 무엇을 보여줄지는 정의하지 않았다. 생성이 60~120초 걸린다면 [가정], "아무 진행 표시도 없고 예상 시간도 말하지 않는" 대기는 정직한 게 아니라 그냥 고장처럼 보인다. **가짜 퍼센트 금지에는 동의하지만, 정직한 대기 설계는 별도로 필요하다.**

## 3. 6개 문답의 UX

**Codex 제안:** 한 화면 한 질문, `현재 질문/전체 질문` 진행 표시, `이전`/`다음` 버튼, 이전 답 자유 수정, 여섯 질문을 하나의 연속 단계로 유지.

### 판단: **[반대]**

세 가지 층위에서 반대한다.

### 3.1 진단과 해법이 어긋난다

Codex안 1.4는 문제를 정확히 짚는다.

> "답을 고른 뒤 매번 같은 CTA를 반복하면 기계적인 설문처럼 느껴진다."

그런데 4.4.7~4.4.8의 해법은 **매 질문 동일한 `이전`/`다음` 버튼 + 숫자 진행 표시**다. 즉 자기가 지목한 원인을 그대로 채택했다. 이것은 문항을 빽빽하게 배치하지 않더라도 구조 자체가 전형적인 설문 위저드이며, `DESIGN_RULES.md`의 "설문지처럼 빽빽하지 않게"라는 원칙이 겨냥한 대상이 바로 이 형식이다. 형식이 아니라 밀도만 조정한 셈이다.

### 3.2 필수 탭 수를 계산하지 않았다

Codex안 4.4.8의 11번 슬롯은 명시적 `다음` 버튼을 유지하는 근거를 이렇게 든다: "오선택 복구와 **첫 질문의 복수 선택 가능성** 때문에 자동 진행보다 명시적 다음을 추천한다."

문제는 **문답 1의 특성(복수 선택일 수 있음) 하나로 문답 2~6(모두 단일 선택 5단계)까지 같은 규칙을 적용했다**는 점이다. 그 비용은 다음과 같다.

| | 필수 탭 | 화면 전환 |
|---|---|---|
| 전 문항 명시적 `다음` (Codex안) | 6선택 + 6다음 = **12탭** | 6회 |
| 문답 1만 명시적 `다음`, 2~6은 선택 즉시 진행 | 6선택 + 1다음 = **7탭** | 6회 |

5탭 차이는 작지 않다. 다만 나도 "선택 즉시 자동 전환"이 오선택 복구를 어렵게 만든다는 Codex의 우려에는 동의하며, 한 Flow 안에 두 가지 진행 규칙이 섞이는 것도 비용이다. **내가 반대하는 것은 결론이 아니라, Codex안이 이 비용을 계산하지도 언급하지도 않은 채 한쪽을 확정했다는 점이다.** 이건 Low-fi에서 A/B로 비교할 항목이지 지금 확정할 항목이 아니다.

### 3.3 가장 큰 반론 — 여섯 문답을 통째로 첫 만남 앞에 둘 이유가 없다

Codex안은 여섯 문답을 "제거할 근거가 없는 원자적 블록"으로 다룬다(1.4, 9.5, 10.2). 나는 이 전제 자체에 반대한다. 여섯 질문이 실제로 언제 쓰이는지 나눠 보면 성격이 다르다.

| 문답 | 쓰이는 시점 | 첫 만남 전에 필요한가 |
|---|---|---|
| 1. 쓰다듬기 선호 부위 | **첫 쓰다듬기 순간** | **필요** |
| 2. 활동량 | 시간에 걸친 자율 이동·놀이 경향 | 불필요 |
| 3. 식사 주기 | 시간에 걸친 자율 식사 리듬 | 불필요 |
| 4. 짖음/울음 정도 | 시간에 걸친 발성 경향 | 불필요 |
| 5. 배변 주기 | 시간에 걸친 흔적 발생 | 불필요 |
| 6. 수면양 | 시간에 걸친 휴식·수면 | 불필요 |

**문답 1만이 첫 만남 직후의 경험(첫 쓰다듬기 → 하트 반응 → "내가 답한 게 반영됐다"는 확인)에 직접 필요하다.** 나머지 다섯은 정의상 시간이 흐른 뒤의 자율 생활에 작용하므로, 첫 만남 후 몇 분 안의 경험에는 관여하지 않는다.

따라서 검토 가치가 있는 대안은 다음과 같다.

> **B안:** 문답 1만 첫 만남 앞에 두고, 문답 2~6은 첫 쓰다듬기 이후 Home 맥락에서 받는다.

이 대안의 장점은 단순히 단계가 줄어드는 게 아니다. **동기의 방향이 뒤집힌다.** 첫 만남 전의 문답은 "아이를 보려면 통과해야 하는 관문"이지만, 첫 쓰다듬기로 개인화가 실제로 작동하는 것을 확인한 뒤의 문답은 "더 우리 아이처럼 만들고 싶다"는 자발적 동기가 된다. 같은 6개 질문이 전혀 다른 심리적 위치에 놓인다.

**공정하게 적어야 할 반론:** 문답 2~6이 미입력인 채로 첫 몇 시간의 자율 생활이 기본값으로 돌아가면, 사용자가 처음 관찰하는 행동이 "우리 아이답지 않게" 느껴질 수 있다. 그런데 "행동/생활 패턴에서 우리 아이 같다고 느끼는가"는 `PRD.md`의 핵심 검증 질문이다. 즉 B안은 첫인상 단계에서 그 가설을 약화시킬 위험이 있다. 또 `PRD.md`는 여섯 문답을 P0로 명시한다(B안은 문답을 제거하는 게 아니라 시점만 옮기므로 P0 위반은 아니라고 본다).

**결론:** A안(현행·Codex안: 여섯 문답 전부 선행)과 B안(문답 1만 선행)은 Low-fi에서 비교해야 할 진짜 갈림길이다. Codex안은 이 갈림길이 존재한다는 사실 자체를 다루지 않았다.

### 3.4 문답 3·5의 정서적 안전성 — Codex안 전체에서 누락

여섯 질문을 톤 측면에서 동일하게 취급한 것도 문제다. **문답 3(식사 주기)과 문답 5(배변 주기)는 반려동물의 투병기·말년 돌봄 기억과 가장 가깝게 맞닿은 두 항목이다.** 마지막 몇 달 동안 잘 먹지 못했던 아이의 보호자는 `하루 1회 미만`을 고르면서 그 시기를 다시 떠올리게 된다. 배변도 마찬가지다.

`AGENTS.md`는 "죄책감, 강요"를 금지하고, `staypet_context.md`는 "관리 의무보다 교감"을 명시한다. 그렇다면 **이 두 질문에서 중립 선택지(`잘 모르겠어요` / `기억나는 대로`)는 편의 기능이 아니라 정서적 안전장치**다. Codex안은 이를 13.2의 미확정 목록에 한 줄 넣었을 뿐, 여섯 질문 사이의 정서적 온도 차이를 전혀 구분하지 않았다.

## 4. 캐릭터 결과 불만족 시 재생성 / 사진 수정 / 보정 관계

**Codex 제안:** `다시 만들기`(동일 입력 재생성) / `사진 수정` / `이전 정보 수정` / `간단 보정`을 원인별로 분리하고, 새 결과가 성공하기 전까지 기존 후보를 보존.

### 판단: **[부분 동의]**

**동의 — 원인별 분리와 기존 결과 보존.** 모호한 단일 `다시 만들기`가 "무엇이 사라지는지 모른다"는 불안을 만든다는 진단은 정확하고, 5.1의 "새 결과가 성공하기 전 기존 결과를 보존한다"는 원칙은 이 Flow 전체에서 가장 잘 쓰인 규칙이다.

**반대 1 — 네 경로를 대등하게 노출하는 것.** 모든 후보가 마음에 들지 않는 순간은 이미 긴 입력과 대기를 통과한, 감정적으로 가장 취약한 지점이다(Codex안 스스로 이탈 위험 2순위로 지목). 그 순간에 "동일 입력 재생성 / 사진 수정 / 정보 수정 / 보정" 4개를 나란히 놓는 것은 **원인 진단이라는 인지 노동을 사용자에게 떠넘기는 것**이다. 사용자는 "왜 안 닮았는지"를 모른다. 그건 시스템도 모르지만, 적어도 시스템은 기본값을 제시할 수 있다.

- 개선 방향: 주 경로 하나(`다시 만들기` = 동일 입력 재생성)를 기본으로 두고, 사진 수정·정보 수정은 한 단계 낮은 위계의 보조 경로로 배치한다. 데이터 보존 원칙은 그대로 유지된다.
- 덧붙여, **`간단 보정`은 애초에 이 그룹에 속하지 않는다.** 보정의 동기는 "전체적으로 만족하지만 부분만 다르다"이고, 나머지 셋의 동기는 "만족하지 않는다"이다. 넷을 하나의 복구 체계로 묶은 프레이밍 자체가 정확하지 않다.

**반대 2 — "동일 입력 재생성"의 무의미 반복 위험을 다루지 않았다.** 같은 입력으로 다시 생성하면 다른 결과가 나오지만 **더 나은 결과가 나온다는 보장은 없다.** 사용자 입장에서 `다시 만들기`는 결과를 예측할 수 없는 반복 시도다. Codex안 4.5.4의 9번 슬롯은 "횟수·비용·대기 제한이 있다면 실행 전에 알려야 한다"까지만 다루고, **반복이 성과 없이 이어질 때의 감정적 소모**는 다루지 않았다. 애도 중인 사용자가 "이번엔 닮게 나올까"를 반복하는 루프는 제품 철학상 특히 경계해야 할 상태다.

- 검토할 대안 1: 재생성에 **방향을 줄 수 있는 최소한의 힌트**(예: 더 밝은 털 / 더 마른 체형)를 강제가 아닌 선택으로 제공한다. Codex안이 "이유 응답은 강제하지 않는다"고 한 판단에는 동의하되, 강제하지 않는 것과 제공하지 않는 것은 다르다.
- 검토할 대안 2: 반복 실패 시 **판단하지 않는 퇴로**(지금은 이대로 두고 나중에 다듬기)를 마련한다. 이는 사용자를 실패 상태에 가두지 않는다.

**반대 3 — 후보 판단을 돕는 element가 하나도 없다.** Codex안에는 후보를 판단할 때 **사용자가 방금 업로드한 원본 사진을 참조할 수단이 없다.** 4.5.2는 "세부 확인용 확대 제공 여부는 사용자 결정이 필요하다"며 확대조차 미정으로 남겼다. `유사도 만족도`는 `PRD.md`의 Quality 지표인데, 그 판단을 작은 카드 이미지와 기억만으로 하게 되어 있다.

- 검토할 대안: 후보 옆에 원본 사진을 참조로 둔다.
- **반론도 함께 적는다:** 원본과 생성 결과를 직접 나란히 놓으면 차이가 더 두드러져 "이건 우리 아이가 아니다"라는 반응을 오히려 강화할 수 있다. 즉 이건 명백한 개선이 아니라 **Low-fi에서 비교해야 할 항목**이다. 다만 Codex안처럼 "선택지 자체를 검토하지 않는" 것은 옳지 않다.

## 5. 이동 가능 영역 지정의 이해와 복구

**Codex 제안:** Brush를 기본 도구로, 지우기 + 실행 취소/다시 실행(신규 추가 추천) + 초기화 + 미리보기 + 완료를 제공하고 최초 1회 짧은 안내.

### 판단: **[반대]**

**동의하는 것은 진단뿐이다.** "첫 사용자의 학습 비용이 가장 큰 단계"(1.7)라는 지적, 제스처 충돌 문제 인식, 정밀함이 아니라 근사 영역으로 성공해야 한다는 원칙 — 모두 맞다.

**해법에 반대한다.** Codex안의 접근은 **"어려운 조작(자유 드로잉)은 그대로 두고, 실수 복구 도구를 추가해 보완한다"**이다. 그 결과 사용자가 이 한 화면에서 마주하는 개념은 다음과 같다.

`칠하기` · `지우기` · `실행 취소` · `다시 실행` · `초기화` · `미리보기` · `완료` — **7개**

여기에 미정 상태인 사진 확대·이동 제스처까지 더해진다. 아무리 안내 문구를 짧게 써도 이것은 **미니 포토에디터**다. 0장에서 지적한 12번 축(대체 가능성)의 부재가 가장 명확하게 드러나는 지점이며, 검토되지 않은 더 단순한 대안이 최소 세 가지 있다.

### 5.1 대안 A — 과업을 "생성"에서 "교정"으로 바꾼다

시스템이 바닥 영역을 먼저 추정해 기본 영역을 제안하고, 사용자는 **틀린 부분만 수정**한다. 사용자의 과업이 "빈 캔버스에 그리기"(어렵다)에서 "제안된 것을 고치기"(쉽다)로 바뀐다. 빈 상태에서 시작하지 않으므로 "어디를 칠해야 하는지 모르겠다"는 최초 진입 장벽 자체가 사라지고, 최소 면적 미달 같은 유효성 실패도 크게 줄어든다. **[가정]** 바닥 추정이 기술적으로 가능한지는 확인이 필요하다.

### 5.2 대안 B — 자유 곡선 대신 블록 단위 토글

바닥 추정이 불가능하다면, 사진 위에 성긴 격자를 얹고 셀을 탭·드래그로 켜고 끄는 방식이 자유 곡선 드로잉보다 오조작 가능성이 훨씬 낮다. 브러시 굵기 개념이 필요 없고, `지우기`는 별도 도구가 아니라 **같은 조작의 반대 방향**(다시 탭하면 꺼짐)이 되므로 도구가 하나 사라진다. 정밀도는 떨어지지만, Codex안 스스로 "정밀 모델링이 아니라 근사 영역으로 성공해야 한다"고 했으므로 요구 정밀도와 어긋나지 않는다.

### 5.3 대안 C — 사진 확대·이동을 아예 제거한다

Codex안이 4.6.2에서 "별도 제스처 규칙이 필요하다"며 미정으로 남긴 제스처 충돌은, **충돌하는 기능 하나를 없애면 사라진다.** 공간 사진 한 장이 화면에 전부 들어와 있고 근사 영역만 필요하다면, 확대·이동은 정밀 작업을 위한 것이지 필수가 아니다. 사진을 고정하면 "한 손가락은 언제나 칠하기"라는 단일 규칙이 성립하고, 모드 혼동과 그로 인한 오조작 한 부류가 통째로 제거된다.

### 5.4 미리보기는 별도 모드일 필요가 없다

Codex안 4.6.6은 미리보기를 "매우 중요"하다고 평가하면서 **들어갔다 나오는 별도 상태**로 설계했다. 그런데 미리보기의 목적은 "지금 칠한 게 어떤 결과를 만드는지 예측"이다. 예측은 편집 중에 연속적으로 필요하지, 마지막에 한 번 확인하는 게 아니다.

- 검토할 대안: 편집 중에 캐릭터(또는 대체 표시)가 **칠해진 영역 안을 계속 돌아다니게 한다.** 예측이 상시 제공되므로 `미리보기` 버튼이 제거되고, "미리보기를 누르지 않고 완료해 버리는" 경로도 사라진다.

### 5.5 이탈 위험 순위에 대한 반론

Codex안 6.1은 이 단계를 이탈 위험 **3순위**로, 사진 업로드를 1순위로 뒀다. 나는 동의하지 않는다.

- 사진 업로드는 **정서적으로** 무겁지만 **조작으로는 익숙하다.** 스마트폰 사용자 대부분이 앨범에서 사진을 고르는 일을 수없이 해봤다.
- 자유형 브러시로 "캐릭터가 다녀도 되는 바닥"을 칠하는 일은 **대부분의 사용자가 생전 처음 하는 조작**이며, 사진 회상 → 문답 → 대기 → 후보 비교로 이미 소모된 직후에 등장한다.
- 게다가 Codex안 6.1의 순위는 **빈도와 심각도를 구분하지 않는다.** 사진 단계 이탈은 빈도가 높을 수 있지만, 후보 불만족은 "핵심 약속이 실패했다"는 회복 불가능한 실망이라 심각도가 가장 크다. 두 축을 하나의 순위로 합치면 완화 우선순위를 정할 수 없다.

## 6. 오브젝트 배치를 첫 만남 전/후 어디에 둘지

**Codex 제안:** 밥그릇·잠자리·장난감의 수동 배치를 첫 만남 **뒤**로 옮긴다. 기술적으로 첫 만남에 오브젝트가 필요하다면 시스템이 임시 위치를 제안하고 사용자가 확인하는 최소 단계로 축소.

### 판단: **[동의]** — 단, 대체안인 "확인 단계"에는 **[반대]**

배치를 첫 만남 뒤로 옮긴다는 결정은 **Codex안에서 가장 설득력 있는 개선안**이다. 후보를 고르고 실제 공간까지 정한 시점은 기대가 최고조인 구간이고, 거기서 오브젝트 3개를 정밀 배치시키면 첫 만남이 "보상"이 아니라 "설정 완료 후 지급되는 것"이 된다. 이 진단에 반론할 지점이 없다.

**반대하는 것은 대체안이다.** "시스템이 임시 위치를 제안하고 사용자가 확인하는 최소 단계"라고 했지만, **확인을 요구하는 순간 그것은 이미 하나의 관문이다.** 첫 만남 직전에 화면을 보고 "확인"을 누르게 하면, 그 순간 사용자는 "우리 집 밥그릇 위치가 저기가 맞나?"를 판단해야 한다. 감정의 흐름은 똑같이 끊긴다. 단계를 줄인 게 아니라 **조작만 가볍게 만든 것**이다.

**대안:** 첫 만남 전에는 오브젝트 관련 UI를 **완전히 제거**하고, 시스템이 조용히 합리적 위치에 배치한 뒤 확인조차 요구하지 않는다. 그러면 오브젝트는 "사용자가 배치한 것"이 아니라 **"원래 그 집에 있던 것"**으로 인식된다. 이는 오히려 제품 컨셉에 더 맞는다 — StayPet은 게임 스테이지를 꾸미는 앱이 아니라 실제 집을 배경으로 하는 앱이고, 실제 집에는 이미 밥그릇이 있었다.

이렇게 하면 두 가지가 깔끔하게 분리된다.

1. **첫 만남에 필요한 것:** 집이 생활감 있게 채워져 있는 상태를 보는 일 → 자동 배치로 충족
2. **첫 만남에 필요 없는 것:** 위치를 직접 정하는 일 → `꾸미기`에서 완전히 선택적으로 발견

**[가정]** 임의의 사용자 공간 사진에서 "합리적인 자동 배치 위치"를 찾을 수 있는지는 기술 확인이 필요하다. 불가능하다면 Codex안의 확인 단계가 차선이 되지만, 그때도 **확인이 아니라 "첫 만남 뒤 첫 배치"로 미루는 쪽**을 먼저 검토해야 한다.

## 7. 첫 만남까지 걸리는 시간과 이탈 위험

**Codex 제안:** 여러 단계에서 화면과 관문을 제거해 첫 만남까지의 경로를 단축.

### 판단: **[부분 동의]**

방향은 옳다. 그러나 **Codex안 전체에 첫 만남까지의 길이를 재는 수치가 단 하나도 없다.** "줄어든다"는 주장은 있는데 얼마나 줄어드는지가 없으면, 다음 토론에서 "이 정도면 충분한가"를 판단할 수 없다. 아래는 내가 `USER_FLOW.md`의 mermaid와 Codex안 12.2를 근거로 계산한 값이다. 추가 사진·동영상·보정을 모두 건너뛴 **최단 경로** 기준이다.

| | 로그인 후 첫 만남까지 화면·상태 수 | 그중 문답이 차지하는 비중 |
|---|---|---|
| 현행 `USER_FLOW.md` | **15~18** (분기 화면 계산 방식에 따라) | 6 / 15~18 |
| Codex 추천안 | **12~13** | **6 / 12~13 ≈ 절반** |
| §3.3의 B안(문답 1만 선행) | **7~8** | 1 / 7~8 |

> **[가정]** 현행 Flow에서 `추가 사진?`·`동영상?`·`보정?` 분기가 독립 화면인지 앞 화면 내부의 분기인지 문서에 명시되지 않아 범위로 표기했다.

이 표에서 나오는 결론이 중요하다.

**Codex안의 개선을 모두 적용하고 나면, 남은 경로의 약 절반이 문답이다.** 기본 정보 통합(-1), 자료 단계 통합(-2), 오브젝트 배치 이동(-1~3)으로 줄일 수 있는 건 다 줄인 상태이고, 그 뒤에 남는 가장 큰 단일 블록이 6개 문답이다. 그런데 Codex안은 문답을 "제거할 근거가 없다"며 검토 대상에서 처음부터 제외했다.

즉 **Codex안은 줄일 수 있는 것을 다 줄인 뒤 가장 큰 덩어리 앞에서 멈췄다.** 여기서 더 줄이려면 §3.3의 B안 같은 재배치를 검토하는 수밖에 없고, 그것을 검토하지 않은 채 "첫 만남까지의 관문을 줄였다"(14.2-1)고 결론짓는 것은 절반만 맞다.

**이탈 위험 순위에 대한 반론은 §5.5에 적었다.** 요약하면 (1) 이동 영역 편집은 3순위가 아니라 1~2순위여야 하고, (2) 빈도와 심각도를 하나의 순위로 합치면 안 된다.

## 8. Home의 직접 상호작용 발견성

**Codex 제안:** 상시 버튼 없이, 캐릭터가 먼저 눈에 띄게 하고 **"사용자가 망설일 때만"** 캐릭터 탭을 1회 안내. 밥·놀이·배변은 실제 상황이 발생할 때 각각 1회.

### 판단: **[부분 동의]**

**동의 — 상시 UI 대신 상황부합형 1회성 안내.** `DESIGN_RULES.md`의 "Dashboard 카드, 숫자 상태 패널, 항상 떠 있는 버튼 다수... 금지"와 정확히 부합하고, 몰입과 발견성의 충돌을 다루는 방식으로 타당하다.

**반론 1 — "망설임"이 정의되지 않았다.** 7.1-3의 "사용자가 망설일 때만"은 설계 원칙처럼 쓰였지만 판정 기준이 없다. N초 무입력인가, 화면을 이리저리 훑는 동작인가, 앱을 배경으로 보냈다 돌아온 것인가? 기준이 없으면 이건 구현 가능한 규칙이 아니라 좋은 의도의 선언이고, **Low-fi에서 검증할 수도 없다.** 최소한 하나의 구체적 후보(예: 첫 만남 종료 후 N초 무입력)로 명시해야 테스트가 성립한다.

**반론 2 — Home 빈 배경 탭이 정의되지 않았다.** Codex안 4.8에는 캐릭터·밥그릇·장난감·배변 흔적·말풍선의 탭이 모두 정의되어 있지만, **기본 시점에서 빈 바닥이나 벽을 탭했을 때 무슨 일이 일어나는지가 53개 element 어디에도 없다.**

이건 사소한 누락이 아니다. "화면 전체가 만질 수 있는 공간"이라고 학습시키려는 설계에서, 사용자의 **최초 탐색 탭은 정확히 빈 곳에 떨어질 가능성이 높다.** 그때 아무 일도 일어나지 않으면 사용자가 배우는 교훈은 "이 화면은 눌러도 안 되는구나"이고, 이는 Codex의 점진적 발견 계획이 무너지는 순간이다. 7.2가 "효과 없는 탭: 화면 전체에 버튼 표식을 늘리기보다 상호작용 대상의 판정과 피드백을 일관되게 한다"고 쓴 것은 **발견성 얘기지 무효 탭의 응답 설계가 아니다.**

- 최소 요구: 유효하지 않은 탭에도 공간이 반응했다는 최소 신호를 준다(캐릭터가 그쪽을 쳐다보는 정도로 충분하다). "아무 일도 없음"과 "인식했지만 대상이 아님"은 사용자에게 전혀 다른 정보다.

**반론 3 — 첫 급식이 무반응일 수 있다.** 4.8.2의 6번 슬롯: "필요 상태면 이동해 먹고, 아니면 먹이가 남아 이후 자연스럽게 이용된다." 즉 **사용자의 생애 첫 급식이 "그릇에 밥이 생겼고 캐릭터는 아무것도 안 함"으로 끝날 수 있다.** 5번 슬롯의 "캐릭터가 가능한 범위에서 이를 인지한다"에서 "가능한 범위에서"는 아무것도 보장하지 않는다.

발견 단계에서 첫 상호작용의 성공 신호가 약하면, 사용자는 그 상호작용을 다시 시도하지 않는다. **배고프지 않을 때도 캐릭터는 반드시 알아차려야 한다**(쳐다보기, 귀 움직임, 한 걸음 다가가기 수준으로 충분하다). 이는 4.8.2의 5·6번 슬롯에 명시되어야 할 규칙이다.

## 9. 캐릭터 탭 → 확대 → 쓰다듬기 → 종료

**Codex 제안:** 탭과 확대를 하나의 연속 동작으로, 쓰다듬기는 부위 문지르기, 종료는 명시적 종료 / 시스템 뒤로가기 / 배경 탭(아래로 스와이프는 쓰다듬기와 충돌하므로 배제).

### 판단: **[부분 동의]**

**동의 — 아래로 스와이프 배제, 탭·확대의 원자적 연결, 종료 시 생활 상태 유지.** 특히 7.3의 "손가락을 뗐다는 이유만으로 바로 기본 시점으로 돌아가지 않는다"는 세밀하고 옳은 판단이다.

**반론 1 — 확대 상태에서 탭을 거부하는 설계는 잘못됐다.** 4.8.6의 7번 슬롯: "짧은 탭이 문지르기로 인식되지 않으면 실패 표시 없이 동작 안내를 한 번 다시 제공한다."

여기에 모드 불일치가 있다. **사용자를 이 상태로 데려온 조작이 바로 탭이다**(4.8.1). 탭해서 확대됐는데, 확대된 곳에서는 탭이 통하지 않고 문지르기만 유효하다. 그리고 그 실패가 하필 **제품에서 가장 중요한 단일 순간인 첫 쓰다듬기**에서 일어난다.

Codex의 해법은 "안내를 한 번 더 제공"이다. 즉 **사용자를 가르쳐서 고친다.** 더 단순한 해법이 있다.

- **탭도 유효한 입력으로 받는다.** 부위 위의 짧은 탭을 아주 짧은 문지르기로 처리해 같은 부위 반응을 준다. 거부할 이유가 없다 — 사용자의 의도는 명확하고, 실패로 처리해서 얻는 것이 없다.
- 이것이 0장에서 말한 12번 축(대체 가능성)의 부재가 만든 전형적 결과다. "안내를 추가한다"는 element를 늘리고, "입력을 받아들인다"는 element를 늘리지 않는다.

**반론 2 — 세 가지 종료 수단을 대등하게 두면 안 된다.** 배경 탭은 **구도에 의존하는 불안정한 종료 수단**이다. 확대 상태에서 캐릭터가 화면의 상당 부분을 차지한다면 탭 가능한 배경이 충분하지 않을 수 있고, 캐릭터가 움직이면 배경 영역도 변한다. "있다가 없어지는 종료 방법"은 종료 방법으로 신뢰할 수 없다.

- 개선 방향: **항상 같은 위치에 존재하는 명시적 종료 수단을 1차 보장**으로 두고, 시스템 뒤로가기와 배경 탭은 보조 편의로 격하한다. Codex안은 셋을 병렬로 나열했지만 여기엔 우선순위가 필요하다.
- 다만 `DESIGN_RULES.md`의 "항상 떠 있는 버튼 다수" 금지와 충돌하지 않는다. **확대 상태에서만** 존재하는 종료 수단 1개는 상시 HUD가 아니다.

**반론 3 — 말풍선과 캐릭터의 탭 의미가 충돌한다.** 4.8.8은 말풍선 탭을 "닫기"로 추천하고, 4.8.1은 캐릭터 탭을 "확대"로 정의한다. 말풍선은 캐릭터 바로 옆이나 위에 뜨는데, 두 개의 인접한 타깃이 정반대 의미를 갖는다. 캐릭터를 만지려다 말풍선을 잘못 누른 사용자는 **원하던 확대를 얻지 못하고 정보만 사라지는** 결과를 얻는다.

- 개선 방향: 말풍선을 **탭 대상에서 완전히 제외**하고 터치를 캐릭터로 통과시킨다. 말풍선은 상태 변화에 따라 스스로 사라진다. Codex안 4.8.8의 11번 슬롯도 "상호작용 CTA일 필요는 없다"고 인정하면서, 4번 슬롯에서는 굳이 탭 닫기를 추천했다. 같은 element 안에서 스스로 모순된다.

## 10. 최소 튜토리얼

**Codex 제안:** 별도 튜토리얼 화면 없이 캐릭터 → 쓰다듬기 → 생활 오브젝트 순으로 상황별 1회 안내. 전체 기능 투어 제거.

### 판단: **[부분 동의]**

**동의 — 투어형 튜토리얼 제거.** 첫 진입에 모든 기능을 설명하는 방식은 몰입을 깨고 기억되지도 않는다는 진단은 옳다.

**반론 1 — PRD의 P0 항목을 조용히 재정의했다.** `PRD.md`의 P0 목록에는 `첫 사용 튜토리얼`이 명시되어 있다. Codex안은 이를 "상황부합형 1회 안내의 총합"으로 해석했는데, **이 해석이 PRD가 의도한 것과 같은지는 어느 문서에서도 확인되지 않는다.** `AGENTS.md`는 "제품 정책이 모호하면 추측해서 확정하지 마라"고 명시한다. 해석 내용 자체에는 반대하지 않지만, **"이것으로 P0 튜토리얼 요구가 충족된 것으로 간주해도 되는가"는 사용자 확인 사항**으로 남아야 한다.

**반론 2 — 점진적 발견이 재방문을 전제하는 순환 구조.** 이게 더 중요한 문제다. Codex안 7.1은 안내를 여러 세션에 걸쳐 분산한다: 캐릭터 탭(1회차) → 쓰다듬기(1회차) → 밥그릇 **또는** 장난감 중 하나(1회차 후반) → 배변 흔적(실제로 처음 생겼을 때, 즉 **아마도 2회차 이후**).

그런데 `PRD.md`의 Primary 지표는 **재방문**이다. 다시 말해:

> **Codex의 발견 설계는 재방문을 전제로 작동하는데, 재방문은 이 제품이 아직 검증하지 못한 바로 그 가설이다.**

사용자가 1회차에서 만난 게 "캐릭터 쓰다듬기" 하나뿐이라면, 다시 돌아올 이유는 그 하나에 전적으로 달린다. 밥·놀이·청소라는 나머지 세 상호작용은 재방문한 사람에게만 전달되므로, **재방문 동기를 만드는 데는 기여하지 못한다.** 순환 의존이다.

- 개선 방향: 1회차에 최소 2개의 직접 상호작용(캐릭터 + 밥그릇 또는 장난감)까지는 도달하도록 설계하고, Low-fi 테스트에서 **"1세션 동안 4개 직접 상호작용 중 몇 개를 스스로 발견했는가"**를 측정 항목으로 삼는다. Codex안 6.4의 관찰 항목에는 "스스로 눌러 보는가"만 있고 개수 측정이 없다.

## 11. 재접속 시 자율적으로 생활했다는 사실을 자연스럽게 이해시키는 방법

**Codex 제안:** 활동 보고서 없이 현재 장면(위치·행동·흔적)만으로 전달. 사용자가 연속성을 이해하지 못하면 **"두 번째 방문에 한해"** 중립적 원리 안내를 검토.

### 판단: **[반대]**

먼저 구분해야 할 것이 있다. **"활동 보고서 없음"은 Codex의 제안이 아니라 `staypet_context.md`의 확정 정책**이다("활동 보고서 팝업은 띄우지 않는다"). 여기에 동의하는 것은 Codex안에 동의하는 것이 아니다. Codex가 실제로 내린 설계 결정은 **"이해 실패에 대한 대비를 2회차로 유예한다"**이며, 나는 이것에 반대한다.

**반대 근거:** 오프라인 자율 생활은 `PRD.md`의 Primary 지표(재방문)와 직결된 핵심 가설이다. 사용자가 "위치가 바뀌었네, 랜덤인가?"라고 오해한 채 지나가면, **검증하려던 질문 자체가 오염된다.** 핵심 가설의 전달 장치를 "이해 못 할 경우의 백업"으로 격하하는 것은 순서가 뒤바뀐 것이다. 게다가 2회차 안내는 정의상 **2회차에 돌아온 사람에게만** 도달하므로, 재방문하지 않은 사람 — 즉 우리가 가장 알고 싶은 집단 — 에게는 영원히 도달하지 않는다.

**대안:** 이 원리를 전달하는 최소 단서를 2회차로 미루지 말고 **첫 재방문 시점의 장면에 결합**한다. 목록형 사건 나열(=보고서)이 아니라 현재 상태를 설명하는 한 줄이면 확정 정책과 충돌하지 않는다. `staypet_context.md`가 이미 허용한 `보리가 지금 쿠션에서 쉬고 있어요.` 계열의 표현과 같은 층위다. 최종 카피는 이 단계에서 정하지 않는다.

**Codex안이 놓친 것 — 재진입 첫 프레임의 캐릭터 가시성.** 3.14는 "가장 먼저 인지해야 하는 정보: 경과시간 결과가 반영된 현재 위치·행동"이라고 쓰지만, **캐릭터가 그 순간 화면에 보인다는 보장이 어디에도 없다.** 시뮬레이션 결과 캐릭터가 가구 뒤에 있거나, 이동 영역 구석에 있거나, 프레임 밖에 있을 수 있다.

재방문의 목적은 `USER_FLOW.md`가 명시한 대로 **"오늘은 아이가 뭐 하고 있을까?"**다. 앱을 열었는데 아이가 안 보이면 그 질문은 답을 얻지 못한다. Primary 지표와 직결된 순간이므로 element 수준의 규칙이 필요하다.

- 최소 요구: 재진입 첫 프레임에서 캐릭터는 **보이거나, 즉시 찾을 수 있어야** 한다. 시뮬레이션 결과가 그렇지 않다면 구도나 진입 시점 처리로 해소한다.

## 12. Low-fi 1차 검증에 필요한 최소 범위

**Codex 제안:** P1 전체 제외(동영상·앨범·추억 사진·알림·상점·함께한 날), P0 핵심 흐름만 검증.

### 판단: **[부분 동의]**

**동의 — P1 제외 기준.** 가격·재화 등 미확정 정책에 의존하는 기능을 1차에서 빼는 판단은 타당하고, 8.2의 기능별 근거도 설득력 있다.

**반론 1 — Codex안 내부 모순.** 8.1 "반드시 검증할 P0 핵심"에는 "이동 영역 뒤 첫 만남으로 바로 가는 추천 순서"가 **이미 확정된 것처럼** 올라 있는데, 13.8 "아직 사용자 결정이 필요한 것"에는 "첫 만남 전 배치안과 첫 만남 후 배치안을 비교 테스트할지"가 **미결로** 올라 있다. 같은 항목이 한 문서 안에서 확정과 미결로 이중 취급된다. Codex안 자체에서 해소되어야 한다.

**반론 2 — 매체 능력과 검증 대상의 불일치 (가장 중요).** 8.1은 다음을 Low-fi에서 "반드시 검증"하라고 한다.

- 이동 영역 Brush·지우기·실행 취소·초기화·미리보기·완료
- Home 캐릭터 발견, 확대, 쓰다듬기, 선호·비선호 반응

**이 두 가지는 정적 Low-fi 와이어프레임으로 검증할 수 없다.** 둘 다 본질이 **제스처와 즉각적 피드백**이기 때문이다. 브러시가 손가락을 따라오는 느낌, 사진 이동과 칠하기의 혼동, 문지르기가 탭으로 오인되는 문제, 하트 반응의 타이밍 — 어느 것도 클릭 가능한 정적 화면으로는 드러나지 않는다. 정적 화면으로 테스트하면 "이해했다"는 **거짓 확신**만 얻고, 실제 문제는 High-fi나 구현 단계에서 처음 발견된다. 이 두 단계는 §5.5와 §7에서 지적한 대로 이탈 위험이 가장 큰 구간이므로, 여기서 거짓 확신을 얻는 것이 가장 위험하다.

- 개선 방향: Low-fi 1차를 **두 종류로 분리**한다.
  - **(A) 화면 흐름 검증** — 정적 와이어프레임으로 가능: 로그인, 기본 정보, 자료 단계, 문답 순서와 진행 이해, 후보 비교·복구 경로 이해, 공간 사진, 첫 만남 → Home 연결, 재방문 진입 장면 이해.
  - **(B) 제스처 검증** — 최소한의 인터랙티브 시제품이나 사람이 반응을 수동으로 재현하는 방식이 필요: 이동 영역 편집, 캐릭터 확대·쓰다듬기·종료.
  - (B)를 (A)와 같은 매체로 처리하지 않는 것이 핵심이다.

**반론 3 — 재방문은 단회 세션으로 검증할 수 없다.** 8.1의 마지막 항목("활동 보고서 없이 달라진 현재 장면으로 들어오는 재방문 상태")은 **시간 경과가 전제**다. 한 번의 테스트 세션에서 이를 확인하려면 경과를 인위적으로 만들어야 하고, 그러면 "며칠 뒤에도 돌아오는가"라는 Primary 가설은 검증되지 않고 **"장면이 바뀐 걸 알아채는가"만** 검증된다. 이 둘을 구분해 기록해야 결과를 오독하지 않는다.

### 13.1 앞 절에서 지적한 누락 (참조)

### 13.2 새로 지적하는 문제

**(13) 품질 실패를 조기에 발견할 지점이 Flow 전체에 없다.**
Codex안 5.1의 복구 원칙은 전부 **기술적 실패**(네트워크, 권한, 저장)를 다룬다. 그런데 이 제품의 가장 치명적인 실패는 **"업로드는 성공했지만 그 사진으로는 닮은 결과가 안 나오는 것"**이다. 이 실패는 사진 단계에서 발생하지만, 사용자에게는 **문답 6개와 생성 대기를 통과한 뒤 후보 화면에서 처음 드러난다.** 그래서 이탈 위험 2순위 지점이 만들어진다.

- 개선 방향: 사진 추가 시점에 최소한의 적합성 신호(얼굴 인식 여부, 지나치게 작음, 피사체가 여럿임)를 제공해 **늦고 비싼 실패를 이르고 값싼 수정으로 전환**한다. 품질 점수를 매기라는 뜻이 아니다 — "이 사진으로 계속할 수 있다"는 최소 확인이면 된다.

**(14) 적합한 사진이 아예 없는 사용자에 대한 처리가 없다.**
흐릿한 사진, 멀리서 찍힌 사진, 사람이나 다른 반려동물과 함께 찍힌 사진만 가진 사용자는 드물지 않다. Codex안 4.3.1은 파일 형식·권한·손상만 다루고, **"쓸 수는 있지만 결과가 안 좋을 사진"**에 대한 경로가 없다. 크롭 유도가 필요한지, 다중 피사체를 어떻게 처리하는지가 전부 비어 있다.

**(15) 접근성 사각지대.**
핵심 상호작용 전부 — 이동 영역 브러시, 오브젝트 드래그, 캐릭터 문지르기 — 가 **정밀한 연속 제스처**다. 대상 사용자(반려동물과 이별한 사람)는 모바일 게임 사용자보다 연령·기기 숙련도 분포가 넓을 가능성이 크다. 손 떨림이나 정밀 터치가 어려운 사용자를 위한 대안 조작이 53개 element 어디에도 없다. §5.2의 블록 토글 대안과 §9의 탭 허용은 접근성 측면에서도 이득이다.

**(16) 생성 결과가 "품질 미달"이 아니라 "정서적으로 불편"할 가능성.**
Codex안 3.7은 후보 불만족을 **유사도 문제**로만 다룬다. 그러나 생성 결과가 어색하게 나올 경우, 애도 중인 사용자에게 이는 단순 품질 이슈가 아니라 정서적으로 견디기 어려운 경험이 될 수 있다. 후보를 처음 보여주는 순간의 기대치 설정과 톤, 그리고 "그만두고 나가는" 안전한 퇴로가 검토되지 않았다.

**(17) 첫 만남 도중 외부 인터럽트 + 다시보기 정책의 자기모순.**
Codex안 4.7.4의 8번 슬롯은 "앱 종료 시 미완료면 안전하게 이어가고"라고 쓰고, 3.11은 "장면을 영구히 놓쳤다고 느끼지 않도록 (…) 다시 보여 주는 정책이 필요하다"고 쓴다. 그런데 **바로 다음 슬롯인 9번은 "수동 다시보기는 현재 범위에 추가하지 않는다"**고 못 박는다. 같은 element의 인접한 두 슬롯이 서로를 부정한다. 그 사이에 전화·알림 같은 **정상 진행 중 인터럽트**는 5.3 표에도 없다. 제품 최대의 감정 정점이 5~10초 1회성이고 복구 정책이 모순 상태라는 것은 그냥 넘어갈 문제가 아니다.

**(18) 다중 반려동물 스코프가 암묵적으로 결정되어 있다.**
`PRD.md`·`USER_FLOW.md` 어디에도 "계정당 반려동물 1마리"라는 제약이 없는데, Codex안 53개 element는 전부 단일 반려동물을 전제한다. 둘 이상을 떠나보낸 사용자는 드물지 않다. 스코프 질문으로 명시해야 한다.

**(19) 애도 대상이 아닌 사용자에 대한 톤.**
현재 살아있는 반려동물로 시도하는 사용자, 호기심으로 써보는 사용자에게 상실을 전제한 카피와 톤이 어떻게 읽히는지가 검증되지 않았다. `staypet_context.md`가 "추모 서비스보다 따뜻한 생활감"을 지향한다면 이 사용자군이 오히려 자연스러운 확장 대상일 수 있다.

**(20) 로그인 우선 배치에 자기 원칙이 적용되지 않았다.**
Codex안 1.1의 대전제는 "첫 가치 경험보다 입력과 설정이 앞선다"이고, 이 원칙을 Flow 전반에 일관되게 적용했다. **단 하나의 예외가 맨 앞의 로그인**이다. 6.1에서 이탈 위험 5순위로 지목하면서도 3.2는 "별도 소개 화면을 추가하는 방식으로 해결하지는 않는다"고만 하고, **인증을 뒤로 미루는 선택지 자체를 평가하지 않았다.**

`CURRENT_STATE.md`가 로그인 첫 화면을 확정했으므로 **이 문서는 변경을 제안하지 않는다.** 다만 Codex가 자신의 제1원칙을 유독 이 지점에만 적용하지 않았다는 비대칭은 기록해 둔다.

## 14. 과도하게 복잡한 부분

**(1) 이동 영역 편집 도구 7종.** 개별 필요성은 각각 인정되지만 총합은 미니 이미지 에디터다. 문제 자체를 단순화하지 않고 도구로 보완한 결과다(§5).

**(2) 간단 보정의 6개 독립 속성.** Codex안 4.5.6의 11번 슬롯은 "여섯 항목을 모두 만지게 강제하면 안 된다"고 하면서, 정작 Element Flow는 귀·털·체형·눈·색·무늬 6개를 **각각 독립적인 조작 대상 + 개별 되돌리기 이력**으로 설계했다. 1차 검증에서 확인해야 할 가설은 "부분 보정이 필요한가"이지 "여섯 속성이 각각 잘 조작되는가"가 아니다. 속성 수를 줄여 가설만 확인하는 편이 낫다.

**(3) 중단 재개 지점(5.5)의 과도한 세분화.** "각 사진 업로드 완료", "각 문답 답변 완료" 단위까지 저장 지점을 나열한 것은 실서비스 안정성 관점에서는 옳지만, **Low-fi 직전 단계에 필요한 해상도를 한참 넘는다.** 이 정도의 상태 영속성 설계는 구현 단계 사안이다.

**(4) 미확정 정책 위에 세운 Element Flow.** 4.9.5(상점)는 "가격·결제·환불 정책은 이 문서에서 정하지 않는다"고 하면서 11개 슬롯을 모두 채운다. 알림(4.9.6)도 마찬가지다. **기반 정책이 없는 상태에서 만든 element flow는 검증할 수 없고, 나중에 정책이 정해지면 대부분 다시 써야 한다.** Codex 스스로 8.2에서 이들을 Low-fi 1차 제외로 분류했으므로, 분석 자체를 후속 단계로 미루는 것이 일관됐다.

## 16. Element-level 재검증 — 핵심 10개

Codex안의 element flow는 11개 축으로 되어 있다. 여기서는 **12개 축**(uxconfirm 기준)으로 다시 검증하되, Codex와 판단이 같은 축은 짧게 확인만 하고 **다르거나 비어 있는 축에 집중**한다.

표기: **[동의]** = Codex안 그대로 / **[보완]** = 방향은 맞으나 빠진 것 있음 / **[반대]** = 다른 설계 필요 / **[신규]** = Codex안에 없음

## 17. 구조 레벨 검증

### 17.1 인지 부하
Codex안 적용 후 화면당 판단 수는 대체로 1개로 잘 정리된다. 예외는 **후보 화면**(선택 + 확정 + 보정 + 3가지 복구 경로 = 최대 6개 판단, §4)과 **이동 영역 화면**(도구 7종, §5)이다. 이 둘이 이탈 위험 상위와 정확히 겹치는 것은 우연이 아니다.

### 17.2 불필요한 단계
Codex안이 잘 제거했다: 추가 사진 분기, 동영상 분기·건너뛰기, 종/이름/성별 분리, 첫 만남 뒤 완료 페이지, 보정의 이중 확정. **추가로 제거 검토 대상:** 성별 필수(§1), 미리보기 별도 모드(§5.4), 오브젝트 확인 단계(§6), 첫 만남 전 문답 2~6(§3.3).

### 17.3 화면 병합
Codex안 10.1의 병합 목록은 대체로 타당하다. 10.2의 "합치지 말아야 할 것"도 동의한다 — 특히 "Home 일반 상태와 오브젝트 배치 상태에서 같은 탭·드래그가 모호하게 두 의미를 갖지 않게" 한다는 규칙은 중요하다. **다만 이 규칙을 Codex 스스로 말풍선(E9)에서 어겼다.**

### 17.4 뒤로가기·수정
5.2 표는 이 문서에서 가장 잘 만들어진 부분이다. 단계별 보존 대상과 확인 필요 시점이 명확하다. **결함 하나:** 병렬 생성을 도입하면 이 표의 전제(직렬 진행)가 무너진다(§2). 표를 병렬 시나리오로 다시 검증해야 한다.

### 17.5 오류 복구
5.1의 8개 원칙, 특히 "실패 범위만 재시도", "새 결과 성공 전 기존 결과 보존", "죄책감·책임 전가 금지"는 제품 철학과 일치하고 그대로 채택할 만하다. **빈 곳은 품질 실패**다 — 전부 기술 실패만 다룬다(§13.2-13).

### 17.6 Empty / Loading / Error
- **Empty:** 잘 다뤘다. "생활 흔적·말풍선이 없는 것은 정상"(3.12), "자료 없음은 정상 빈 상태"(4.9.3)는 옳다.
- **Loading:** 가짜 진행률 금지는 옳지만 **대안이 없다**(§2-3). 병렬화 실패 시 대기 경험이 미설계다.
- **Error:** 5.3 표로 충분히 다뤘다.

### 17.7 이탈 가능 지점
Codex안 6.1의 5개 지점 식별은 타당하나 **순위와 축이 문제**다: 이동 영역은 3순위가 아니라 1~2순위여야 하고(§5.5), 빈도와 심각도를 하나로 합쳐서는 완화 우선순위를 못 정한다(§7).

### 17.8 기대와 실제 동작의 불일치
발견된 것 3개, 모두 element 수준:
1. **밥그릇** — "주면 먹는다"고 기대하지만 배고플 때만 먹는다(E8).
2. **확대 상태의 탭** — 탭으로 들어왔는데 탭이 안 통한다(E7).
3. **`다시 만들기`** — "다시 하면 나아진다"고 기대하지만 보장이 없다(E4).

### 17.9 TTFV (첫 핵심 가치까지의 시간)
§7의 표 참조. 현행 15~18 → Codex안 12~13 → 문답 재배치 시 7~8. **TTFV를 더 줄이는 유일하게 남은 큰 레버는 문답 블록이며, Codex안은 이를 검토 대상에서 제외했다.**

또한 이 제품의 "첫 핵심 가치"는 하나가 아니라 둘로 나뉜다는 점을 지적한다.

- **가치 A: "우리 아이가 우리 집에 있다"** — 첫 만남에서 도달
- **가치 B: "내가 답한 것이 반영됐다"** — 첫 쓰다듬기 하트 반응에서 도달

Codex안은 A까지의 경로는 최적화했지만 **B까지의 경로는 "망설일 때만 안내"라는 미정의 트리거에 맡겨 두었다**(§8). B는 이 제품의 차별점을 사용자가 처음 체감하는 지점이므로, A만큼 확실하게 도달을 보장해야 한다.

## 20. 다음 토론 단계에서 결정해야 할 것

이 문서는 최종 합의안을 만들지 않는다. 아래는 **Codex안과 이 문서의 의견이 실제로 갈려서 결정이 필요한 지점**만 추린 것이다. Codex안 13장의 미결 항목들은 이 문서도 동일하게 미결로 둔다.

### 결정 1 — 이동 영역 편집의 근본 형태

| 선택지 | 내용 |
|---|---|
| **A (Codex)** | 자유 브러시 유지 + 실행 취소/다시 실행 추가 |
| **B (본 문서 1안)** | 시스템이 바닥을 추정해 제안 → 사용자는 교정만 |
| **C (본 문서 2안)** | 블록 단위 탭 토글 |

세 안 모두 사진 확대·이동 제거(§5.3)와 미리보기 상시화(§5.4)를 함께 적용할 수 있다. **B는 기술 확인이 선행되어야 한다.**

### 결정 2 — 여섯 문답의 위치

| 선택지 | 첫 만남까지 화면 수 | 위험 |
|---|---|---|
| **A (Codex)** 여섯 문답 전부 첫 만남 앞 | 12~13 | TTFV의 절반이 설문 |
| **B (본 문서)** 문답 1만 앞, 2~6은 첫 쓰다듬기 뒤 | 7~8 | 첫 관찰 시 행동이 기본값이라 "우리 아이 같다"가 약해질 수 있음 |

Low-fi에서 비교할지, 한쪽으로 확정할지 결정이 필요하다.

### 결정 3 — Low-fi 1차의 매체와 분할

| 선택지 | 내용 |

### 확인이 필요한 `[가정]` 목록
